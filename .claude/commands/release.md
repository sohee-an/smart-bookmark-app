운영 릴리스 전에 UX를 한 번 본다. UX는 바뀐 한 줄이 아니라 여러 화면이 합쳐졌을 때 문제가 생기므로, 변경마다가 아니라 릴리스 묶음 단위로 본다. 결과는 리뷰 보관소 문서 한 곳에만 남긴다 (PR 코멘트로 달지 않는다).

추가 인자: $ARGUMENTS

## 1. 범위 고르기 (AI 없이)

```
git fetch origin
node scripts/release/ux-scope.mjs $ARGUMENTS
```

- 마지막 줄 JSON의 `selected`가 비어 있으면 "바뀐 화면이 없어 UX 리뷰를 건너뜁니다"라고 알리고 3번으로 간다.
- `skipped`가 있으면 예산 밖이라 리뷰하지 않은 파일이다. 사용자에게 개수와 목록을 보여 준다.

## 2. UX 리뷰 (ux-critic 에이전트, 범위 제한)

ux-critic 에이전트를 아래 지시로 부른다. 토큰을 아끼는 것이 목적이다.

```
릴리스 UX 리뷰다. 먼저 .claude/project/release/ux-scope.md 하나만 읽는다. 거기에 지난 릴리스 이후 바뀐 화면 파일과 변경분이 있다.
- 범위: 그 문서의 "선택" 파일과 화면 묶음만. 제외된 파일은 보지 않는다.
- 파일을 직접 여는 건 변경분만으로 판단이 안 될 때만, 전부 합쳐 5개까지.
- 화면 흐름 단위로 본다 (예: "검색하고 결과를 보고 태그를 바꾸는 흐름"). 컴포넌트 하나의 미세한 스타일은 보지 않는다.
- 이슈는 최대 7개. "심각"(사용자가 막히거나 잘못 이해함)과 "개선" 두 단계만. 잘된 점과 일반론은 쓰지 않는다.
- 이슈마다: 화면 흐름, 파일:줄, 어떤 사용자가 어디서 막히는지, 고치는 방법 한 줄.
- 마지막 줄: "검토 범위: 화면 파일 N개, 제외 M개, 직접 연 파일 K개"
```

결과를 `.claude/project/reviews/ux-review-YYYY-MM-DD.md`에 저장한다 (같은 날 파일이 있으면 `-2`를 붙인다). 리뷰 보관소 규칙(CLAUDE.md "리뷰 결과 보관소")을 따른다.

## 3. 릴리스 PR

- `git log --oneline origin/main..origin/dev --merges`로 포함된 PR을 모은다.
- `gh pr create --base main --head dev`로 PR을 연다. 본문에 포함된 PR 목록과 한 줄을 남긴다: "UX 리뷰: 리뷰 보관소 ux-review-YYYY-MM-DD.md (심각 N, 개선 M)" 또는 "UX 리뷰: 바뀐 화면 없음".
- **머지하지 않는다.** main 머지는 사람이 매번 정한다. PR 링크와 UX 리뷰 요약(심각 이슈 제목만)을 보여 주고 끝낸다.
