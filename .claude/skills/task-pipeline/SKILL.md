# Notion 태스크 파이프라인

이 문서가 Notion 워크플로우의 **유일한 기준**이다. CLAUDE.md와 명령(`new-task`, `notion-review`)은 여기를 가리키기만 한다. 흐름을 바꾸면 여기만 고친다.

같은 폴더의 참고 문서:

- 상태값과 전환: STATUS.md
- 시나리오 쓰는 법: SCENARIO.md
- 5회 실패 처리: ESCALATION.md

## 0. 준비: Notion 도구와 ID

- 도구는 claude.ai Notion 커넥터(`mcp__claude_ai_Notion__*`)를 쓴다. 쓰기 전에 ToolSearch로 필요한 도구를 한 번에 불러온다.
- ID는 로컬 설정 `.claude/project/notion.json`에 둔다 (git 제외 폴더). 형식은 같은 폴더의 `notion.example.json`.
- 설정이 없거나 비어 있으면 `notion-search`로 "할일 매니저"를 찾고, 찾은 ID를 사용자에게 보여 주고 설정 파일에 채운다. 매번 검색하지 않는다.
- `notion-query-data-sources`의 SQL은 한 번에 **데이터 소스 하나만** 넣는다. 여러 개를 한 쿼리에 넣으면(UNION 등) Business 플랜이 아니면 거절된다.

## 1. "새 할일 등록해줘 [내용]"

1. **큰 할일:** 할일 매니저 안의 "큰 태스크 목록" DB에 행을 하나 추가한다 (할일 매니저 아래에 페이지를 새로 만들지 않는다). 상태는 `진행중`.
2. **세부 태스크 DB:** 큰 할일 페이지 안에 세부 태스크 DB를 만든다. 스키마는 아래 "세부 태스크 DB 스키마" 그대로. 기존 DB를 복사해 맞추지 않는다.
3. **태스크 분해:** CLAUDE.md "태스크 분해 기준"대로 **브라우저나 앱에서 눈으로 확인할 수 있는 동작 단위**로 나눈다. 파일 단위로 나누지 않는다.
4. **각 태스크 페이지:** 생성과 동시에 두 섹션을 쓴다.
   - `## 테스트 시나리오`: SCENARIO.md 기준 (Given / When / Then, 정상, 오류, 엣지)
   - `## 시나리오 피드백`: 빈 섹션 (사람이 의견을 적는 곳)
5. 상태는 `테스트 시나리오`, 두 체크박스는 false. 코드 방향(관련 코드, 구현 계획)은 아직 쓰지 않는다. 시나리오검수 뒤에 쓴다.

## 2. "노션 댓글 확인해줘"

두 가지를 순서대로 한다.

### 2-0. 대상 찾기

1. 큰 태스크 목록(`bigTaskDataSourceId`)에서 상태가 `완료`가 아닌 행을 조회한다.
2. 각 큰 할일 페이지를 fetch해서 본문의 세부 태스크 DB(`data-source-url`)를 얻는다.
3. 세부 태스크 DB를 하나씩 조회한다.
4. 명령에 큰 할일 이름이 붙어 있으면(`노션 댓글 확인해줘 [큰 할일 이름]`) 그 큰 할일만 대상으로 한다. 이름이 없으면 전부가 대상이므로, 상태를 바꾸기 전에 바뀔 태스크 목록을 사용자에게 먼저 보여 준다 (오래된 실제 할일이 함께 움직일 수 있다).

### 2-1. 댓글 확인과 답글

- 대상: 2-0에서 찾은 세부 태스크 중 상태가 `완료`가 아닌 페이지.
- **새 댓글 판별:** 스레드의 마지막 댓글이 `[AI]`로 시작하지 않으면 답할 차례다. 사람과 AI가 같은 Notion 계정을 써서 작성자로는 구분할 수 없기 때문이다. `notion-get-comments`는 대괄호를 이스케이프해서 `\[AI\]`로 돌려준다. 역슬래시를 빼고 비교한다.
- 답글은 항상 `[AI] `로 시작한다. 맥락(시나리오, 구현 계획, 앞선 댓글)을 읽고 답한다.
- 댓글이 질문이면 답하고, 결정이 필요한 질문이면 **사람에게 되묻는다.** AI가 혼자 "이렇게 바꾸겠습니다"로 정하지 않는다. 결정된 내용만 시나리오나 계획에 반영한다.

### 2-2. 체크박스 감지와 단계 진행

세부 태스크 DB 전체를 조회하고, 태스크마다 아래 표의 조건에 맞는 단계를 실행한다.

| 조건 | 할 일 |
| --- | --- |
| 상태가 비어 있음, 또는 본문에 `## 테스트 시나리오`가 없음 | 1번 4~5단계대로 시나리오 작성, 상태 `테스트 시나리오` |
| `테스트 시나리오`, 시나리오검수=false, 시나리오 피드백 없음 | 대기 |
| `테스트 시나리오`, 시나리오검수=false, 시나리오 피드백 있음 | 피드백 반영해 시나리오 재작성, 피드백 섹션 비움, 대기 |
| `테스트 시나리오`, 시나리오검수=true | 상태 `방향성`, 3번(구현 계획 + 테스트 코드, 실패 확인) 작성 |
| `방향성`, 개발구현방향=false, 방향 피드백 없음 | 대기 |
| `방향성`, 개발구현방향=false, 방향 피드백 있음 | 피드백 반영해 구현 계획 재작성, 피드백 섹션 비움, 대기 |
| `방향성`, 개발구현방향=true | 4번(구현) |
| `개발중`, `테스트중` (앞선 실행이 중간에 멈춘 경우) | 사람에게 알리고 대기. 혼자 다시 시작하지 않는다 |
| `완료`, `재검토필요`, `재개발`, `검수요청` | 대기 (`재개발`은 사람이 지시한 댓글대로 4번을 다시 실행) |

**체크박스는 사람만 누른다. AI는 체크박스를 바꾸지 않는다.** 체크 없이 다음 단계로 가지 않는다.

시나리오나 구현 계획을 새로 쓰거나 고쳤으면 `[AI]` 댓글 한 줄로 무엇이 바뀌었는지 알린다. 페이지 본문만 바뀌면 사람이 알아차리기 어렵다.

**댓글 위치:** `page_id`만 주고 댓글을 달면 기존 페이지 스레드에 붙는다. 새 주제(구현 계획 작성 알림, 완료 요약)는 `selection_with_ellipsis`로 해당 제목(예: `## 구현 계획`)에 붙여 새 스레드로 연다. 사람 댓글에 대한 답은 그 스레드의 `discussion_id`로 단다.

## 3. 구현 계획과 테스트 코드 (시나리오검수=true 뒤)

사람이 **구현 전에 테스트 코드를 보고** 승인하게 한다. 코드가 아니라 테스트를 승인하는 것이 이 파이프라인의 핵심이다.

1. 작업 브랜치를 만든다 (`task/<태스크 요약>`, origin/dev 기준). 이 단계의 커밋은 로컬에만 둔다.
2. 승인된 시나리오를 테스트로 옮긴다 (위치는 CLAUDE.md "테스트 파일 컨벤션"). 테스트 이름에 시나리오 문장을 쓴다.
3. 테스트를 돌려 **실패하는 것(Red)을 확인한다.** 구현 전인데 통과하는 테스트가 있으면 시나리오나 테스트가 틀린 것이니 고친다.
4. 페이지에 네 섹션을 추가한다.
   - `## 관련 코드 수집`: 실제로 파일을 읽고, 연관 파일 경로, 재사용할 타입, 함수, 컴포넌트, 새로 만들 파일. 경로는 PROJECT_INDEX.md 기준.
   - `## 테스트 코드`: 테스트 파일 경로, 테스트 이름 목록, 핵심 단정 몇 줄, 실패(Red) 결과 요약.
   - `## 구현 계획`: 시나리오 기준의 구현 방향, 수정할 파일, 핵심 흐름.
   - `## 방향 피드백`: 빈 섹션. 테스트나 계획이 마음에 안 들면 사람이 적는다.
5. `[AI]` 댓글로 "테스트 N개 작성, 모두 실패 확인, 확인 후 개발구현방향을 체크해 주세요"를 남긴다.

## 4. 구현 (개발구현방향=true 뒤)

1. **상태를 먼저 `개발중`으로 바꾼다.** 사람이 Notion에서 지금 AI가 작업 중인지 알 수 있어야 한다.
2. `## 방향 피드백`에 내용이 있으면 반영한다.
3. **승인된 테스트를 통과하도록 구현한다.** 3번에서 사람이 본 테스트는 고치지 않는다. 테스트를 바꿔야 하면 구현을 멈추고 `[AI]` 댓글로 이유를 남겨 사람에게 묻는다.
4. 구현 중 시나리오에 없던 경우를 발견하면 테스트를 더할 수는 있다. 더한 테스트는 완료 댓글에 따로 적는다.
5. 상태 `테스트중`, 현재 태스크와 관련 파일의 회귀 테스트를 돌린다: `pnpm --filter @smart-bookmark/web exec vitest run <테스트 파일...>`. 바꾼 컴포넌트를 렌더링하는 테스트(import로 찾음)도 넣는다. 테스트가 실패하면 pnpm이 `Command "vitest" not found`를 덧붙여 출력하는 경우가 있다. 판정은 vitest의 실패 출력으로 한다.
6. 결과:
   - 전부 통과: 상태 `완료`, 완료 댓글(`[AI]`로 시작). 댓글에 **사람이 화면에서 확인할 것**을 따로 적는다. 단위 테스트만으로는 "눈으로 확인"이 끝나지 않는다.
   - 실패: 스스로 고쳐 다시 돌린다. 실패할 때마다 `실패횟수`를 1 올린다.
   - 5회 실패: ESCALATION.md대로 `검수요청`.
7. 큰 할일의 세부 태스크가 모두 `완료`면 큰 할일도 `완료`. 세부 태스크 DB를 상태별로 세어(`GROUP BY 상태`) 확인한다.

## 세부 태스크 DB 스키마

| 속성 | 타입 | 값 |
| --- | --- | --- |
| 태스크명 | Title | 동작 단위 문장 |
| 상태 | Select | 테스트 시나리오, 방향성, 개발중, 테스트중, 완료, 재검토필요, 재개발, 검수요청 |
| 시나리오검수 | Checkbox | 사람이 시나리오를 승인 |
| 개발구현방향 | Checkbox | 사람이 구현 계획을 승인 |
| 실패횟수 | Number | 테스트 연속 실패 횟수 |
| 관련파일 | Text | 관련 코드 수집에서 찾은 파일 |

## 사람 경계와 한계

- 사람이 정하는 것: 시나리오검수, 개발구현방향, 결정이 필요한 댓글, 검수요청 이후 방향, 재개발.
- **한계:** AI와 사람이 같은 Notion 계정을 쓰면 Notion에서는 누가 체크했는지 구분할 수 없다. 지금은 AI가 이 문서를 지키는 것에 기댄다. 확실하게 하려면 AI 전용 Notion 통합(봇)을 따로 두어 작성자를 가른다.
