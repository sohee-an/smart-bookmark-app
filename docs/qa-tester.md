# QATester: 근거가 있는 QA 지식 장부

제품이 "이 조건에서 이렇게 동작한다"는 사실을, 실제 테스트 실행 결과와 근거를 붙여 쌓는다.
코드가 바뀌면 그 코드에 걸린 사실만 "재검증 필요"가 되고, 그것만 다시 돌린다.

## 개념

| 개념                       | 뜻                                                                                  | 누가 만드나                                             |
| -------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 시나리오                   | 사용자 동작 단위의 주장. 예: "비회원은 20개까지 저장하고 21번째에 한도 안내가 뜬다" | 사람 (나중엔 에이전트가 초안)                           |
| 검증 테스트 (`verifiedBy`) | 그 주장을 확인하는 테스트                                                           | 사람. 테스트 작성 에이전트는 추가만 (hook이 강제)       |
| 연결 (links)               | 시나리오가 의존하는 코드 파일                                                       | **기계** (import 그래프 + E2E 라우트 → App Router 파일) |
| 사실 (facts)               | 실행 결과 + 근거: 커밋, 시각, 연결된 파일의 내용 해시                               | **기계** (`recheck`). 지우지 않고 쌓기만 한다           |
| 신선도                     | 마지막 통과 때의 파일 해시와 지금 해시를 비교                                       | **기계**                                                |

상태는 일곱 가지다.

| 상태                | 뜻                                                                                              |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| 통과 (fresh)        | 모든 검증 테스트가 마지막 실행에서 통과했고, 그 뒤 연결된 코드가 그대로다                       |
| 부분 검증 (partial) | 한 번도 안 돈 검증 테스트가 있거나(예: E2E), skip된 테스트가 있다. 통과로 세지 않는다           |
| 재검증 필요 (stale) | 검증 뒤 연결된 코드나 시나리오 정의(주장, 검증 테스트, 주기)가 바뀌었거나 외부 의존 주기가 지남 |
| 실패 (failing)      | 검증 테스트가 실제로 실패했다. 제품이 주장대로 동작하지 않을 수 있다                            |
| 검사 오류 (broken)  | 검사 자체가 돌지 못했다 (환경, 도구, 외부 한도, 근거 테스트가 사라짐). 제품 실패로 세지 않는다  |
| 미검증 (unverified) | 검증 테스트가 없거나 아직 한 번도 돌지 않았다                                                   |
| 보류 (hold)         | 사람이 미뤄 둔 시나리오                                                                         |

판정은 검증 테스트마다 따로 한다. 테스트마다 "마지막으로 실제로 돈 기록"을 골라서 보기 때문에, E2E 없이 돌린 통과가 이전의 E2E 실패를 덮지 않는다.
근거에는 실제로 걸린 테스트 제목이 남는다. 같은 정의에서 다음 실행 때 그중 하나가 사라지면(이름이 바뀌거나 지워짐) 통과가 아니라 검사 오류로 멈춘다.
`maxAgeDays`가 있는 시나리오(AI 응답처럼 외부에 달린 것)는 코드가 그대로여도 기간이 지나면 재검증 필요가 된다.

## 사용

```bash
node scripts/qa/qa.mjs status                    # 전체 상태
node scripts/qa/qa.mjs show bookmark.guest-limit # 연결된 코드, mock된 경계, 마지막 근거
node scripts/qa/qa.mjs recheck                   # 재검증 필요한 것만 다시 돌리고 사실을 쌓는다
node scripts/qa/qa.mjs recheck --e2e             # Playwright까지 (브라우저, 개발 서버 필요)
node scripts/qa/qa.mjs recheck --all             # 전부 다시
node scripts/qa/qa.mjs recheck --live            # 실제 AI 점검처럼 외부 서비스를 부르는 검사까지 (로컬 Supabase 필요)
node scripts/qa/qa.mjs recheck --scenario a,b    # 지정한 시나리오만
node scripts/qa/qa.mjs fact void <시나리오> --last --reason "<이유>"   # 환경 탓 근거를 무효로 표시 (지우지 않음)
```

검증 테스트의 `name`은 부분 문자열이거나 `/정규식/`이다. 넓게 걸리는 이름(예: "실패")은 쓰지 말고 테스트 제목을 정확히 적는다.

### 근거를 무효로 할 때

근거(facts)는 지우지 않는다. 외부 한도 초과처럼 제품과 무관한 이유로 실패가 기록됐으면 `fact void`로 무효 기록을 덧붙인다. 그 근거는 판정에서 빠지고, 무효로 한 이유는 장부에 남는다.
무효 처리는 사람이 정한다. 실패를 지우고 싶어서 쓰는 명령이 아니다.

## 실제 AI 점검 (`--live`)

`scripts/qa/live-check.mjs`가 진짜 크롤링과 Gemini로 고정 URL 3개를 저장해 제목, 요약, 태그(1~8개)가 채워지는지 본다.
요약 문장은 매번 달라서 비교하지 않는다. 테스트 계정은 그 자리에서 만들고 끝나면 지운다.

- 데이터는 **로컬 Supabase**(Docker)에만 들어간다. 실제 DB는 건드리지 않는다. 먼저 `npx supabase start`
- 앱 서버는 3200 포트에 로컬 Supabase 주소로 따로 뜬다. Gemini 키는 `.env.local`에서 읽는다
- 시나리오 `bookmark.pipeline.real-ai`, `extension.save.api`가 이 스크립트로 검증되고, `maxAgeDays: 1`이라 하루 지나면 재검증 필요가 된다
- 검사는 그룹으로 나뉜다. `api`(저장 API, 토큰 없음과 틀린 토큰의 401), `ai`(실제 AI 결과), `setup`(계정 생성과 삭제, 서버 기동). `setup`이 실패하면 검사 오류다
- Gemini 429(한도 초과)로 AI 검사가 실패하면 `setup:ai`로 올라가서 실제 AI 시나리오만 검사 오류가 된다. 저장 API 시나리오는 영향받지 않는다
- 비용: 실행 1회에 크롤링 3회, Gemini 요약 3회, 임베딩 3회

| ----------------------------------------- | ---------------------------------------------------------- | ----------------------- |
| `scripts/qa/lib.mjs`, `scripts/qa/qa.mjs` | 엔진, CLI                                                  | 그대로 복사             |
| `qa-knowledge/config.json`                | 앱 위치, tsconfig, 테스트 명령                             | 새로 쓴다               |
| `qa-knowledge/scenarios.json`             | 시나리오                                                   | 새로 쓴다               |
| `qa-knowledge/facts.jsonl`                | 실행 근거 (커밋한다)                                       | 비워서 시작             |
| `scripts/qa/live-check.mjs`               | 실제 AI 점검 (runner `script`의 예)                        | 앱에 맞게 새로 쓴다     |
| `supabase/config.toml`                    | 로컬 Supabase 설정 (QA용으로 Studio 등 끔, 이메일 인증 끔) | 새로 쓴다               |

엔진은 Node만 있으면 되고 외부 패키지를 쓰지 않는다. 현재 지원: TypeScript/JavaScript import, tsconfig paths, Vitest, Playwright, Next.js App Router 라우트, 그리고 JSON 결과를 내는 임의 스크립트(runner `script`).

## 2단계: 에이전트 (사람 관문 있음)

`/qa-sweep [기능]`으로 한 바퀴 돈다. 세 에이전트는 서로의 결과를 보지 않는다.

| 에이전트             | 하는 일                                                                            | 쓸 수 있는 파일                                   | 모델   |
| -------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------- | ------ |
| `qa-scenario-writer` | 기획서, 코드, `gaps`를 보고 시나리오 후보 제안                                     | `qa-knowledge/proposals/`에 새 파일 하나          | Sonnet |
| `qa-test-author`     | 승인된 시나리오를 테스트로 작성하고 실행                                           | 테스트 파일, 픽스처, 해당 시나리오의 `verifiedBy` | Sonnet |
| `qa-judge`           | 실패를 app-bug / test-bug / claim-too-wide / flaky-external / env / unclear로 판정 | 없음 (읽기 전용)                                  | Opus   |

사람 관문: 제안을 장부에 넣는 것, 이슈나 PR을 만드는 것. 작성 에이전트는 앱 코드를 고치지 않는다.

## 3단계: 나이틀리

`node scripts/qa/nightly.mjs`가 재검증 필요한 것만 돌리고 `qa-knowledge/reports/YYYY-MM-DD.md`를 남긴다.
외부에 달린 검사(`maxAgeDays`)가 실패하면 한 번 더 돌리고, 직전 보고서에서도 실패였으면 "연속 실패"로 올린다. 종료 코드는 연속 실패가 있을 때만 1이다.

GitHub Actions(`qa-nightly.yml`)는 매일 03:00 KST에 dev 기준으로 돌고 **보고만** 한다.

- 결과는 그 실행의 요약(Job Summary)과 보고서 아티팩트(30일)로만 남는다. **이슈를 만들지 않는다.** 공개와 이슈 등록은 사람이 정한다
- CI에서 쌓인 근거는 올리지 않는다. 장부는 로컬에서 돌리고 사람이 커밋한 것 하나다 (두 갈래가 되지 않게)
- 공개 저장소라 `private: true`인 시나리오(보안 미검증 등)와 실행 로그는 CI 보고서에서 뺀다
- 연속 실패 판정과 종료 코드 1은 로컬 나이틀리에서만 한다. CI는 항상 0

## 발견 장부

점검 중 눈에 띈 문제는 `node scripts/qa/qa.mjs finding add <id> "<내용>"`으로 `qa-knowledge/findings.jsonl`에 적는다.
상태는 open / fixed / wontfix / observed. 같은 id로 다시 add하면 상태가 바뀐다(이전 기록은 남는다).

## 테스트 작성 에이전트 제한 (hook)

테스트 작성 에이전트가 앱 코드를 고쳐서 테스트를 통과시키거나, 실패하는 테스트를 판정 기준에서 빼면 장부가 거짓 통과를 낸다. 에이전트 문서의 부탁으로는 막히지 않아서 hook으로 강제한다. 에이전트 파일 머리말에 걸려 있어서 그 에이전트가 돌 때만 동작한다.

| 도구           | 허용                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------- |
| Write, Edit    | `*.test.ts(x)`, `apps/web/e2e/*.spec.ts`, 테스트 픽스처                                           |
| scenarios.json | `verifiedBy`에 항목 추가만. 기존 항목 수정, 삭제, 주장이나 보류 같은 다른 필드 변경은 막힘        |
| Bash           | 테스트 실행, 장부 명령(status, show, recheck, gaps), 읽기 전용 git. 리다이렉트, 파이프, 치환 금지 |

hook이 못 보는 구멍은 테스트 코드가 실행 중에 파일을 쓰는 경우다. 에이전트가 끝나면 `--check-diff`로 작업 트리를 사후 점검한다(qa-sweep 4단계).

## 한계 (알고 쓸 것)

- **mock된 경계는 검증되지 않는다.** 테스트가 `vi.mock`이나 `page.route`로 바꾼 모듈과 API는 연결에서 빠지고 `show`에 따로 표시된다. 그 코드가 바뀌어도 이 시나리오는 재검증 필요가 되지 않는다
- **문자열로 부르는 API는 리터럴만 본다.** `fetch("/api/crawl")`, ``fetch(`/api/collections/${id}`)``, `axios.get("/api/x")`, Playwright `request.post("/api/x")`, 그리고 `const URL = "/api/x"`를 fetch에 바로 넘기는 경우까지는 App Router의 `route.ts`에 잇는다
  - E2E: 실제 서버가 뜨므로 route까지 잇는다. `page.route`로 가짜 응답을 준 API는 잇지 않고 `show`에 "실행되지 않는 API"로 따로 보인다
  - 단위 테스트: 서버가 없어서 잇지 않고 같은 목록에 남긴다. route 핸들러를 직접 import하는 테스트는 import 그래프로 이미 연결된다
  - 변수로 조립한 주소, 래퍼 함수 안에서 만드는 주소, 외부 도메인 호출은 여전히 못 본다. 동적 세그먼트(`${id}`)는 그 자리에 `[param]` 디렉터리가 하나일 때만 잇는다
  - 기능 플래그로 숨긴 화면의 API도 import만 되어 있으면 연결된다 (예: 컬렉션). 넓게 잡히는 쪽이다
- **연결은 넓게 잡힌다.** 화면 하나를 타면 레이아웃과 헤더까지 딸려 온다. 그래서 헤더를 고치면 E2E 시나리오 대부분이 재검증 필요가 된다. 놓치는 것보다 낫지만 E2E 비용은 늘어난다
- **skip된 테스트는 확인되지 않은 것이다.** 로그인 계정이 없어 skip되는 E2E가 있으면 그 시나리오는 계속 부분 검증으로 남는다. 다시 돌려도 바뀌지 않아서 나이틀리 대상에서는 뺀다
- **근거 테스트가 주장과 맞는지는 기계가 모른다.** 근거에 남은 테스트 제목을 사람이 읽고 판단해야 한다 (`show`)
