## 1. 노션 검수 파이프라인: 한번 써 본 것 (2분)

**화면**: 노션 세부 태스크 DB 하나 (사이드바 접고 링크로 직접 열기). 이어서 큰 할일 "[워크플로우 테스트 3] 북마크 카드에 '읽은 지 N분 전' 표시"(https://app.notion.com/p/3f9d9ab99d638189a7a4e353cfe890e8)를 열어 작은 태스크 4개가 단계별로 있는 것을 보여 주고, 방향성 태스크 "읽은 시각 전용 필드"(https://app.notion.com/p/3f9d9ab99d63811883c7cf4e50ac6d14)를 열어 "테스트 코드" 섹션을 보여 준다. 시간 되면 완료 사례 페이지의 "RHF는 오버엔지니어링" 피드백

> 개인 프로젝트에 Claude Code를 몇 달 붙여 쓰면서 하네스가 어떻게 바뀌었는지 공유하려고 합니다. 실제로 겪은 순서대로 갈게요.
>
> 처음엔 거창한 생각은 없었어요. 노션에 에이전트를 붙여서 한번 써 보자, 검토는 내가 하고 개발은 AI한테 맡겨 보자, 그 정도였습니다. 할일을 하나 등록하면 AI가 동작 단위로 태스크를 나누고 시나리오를 써요. 제가 시나리오를 체크하면 AI가 테스트 코드를 먼저 올리고, 그 테스트를 보고 한 번 더 체크하면 그때 구현합니다.
>
> 써 보니 코드가 아니라 시나리오와 테스트를 승인하는 건 괜찮았어요. AI가 폼 라이브러리를 들여오겠다는 계획을 올렸을 때, 코드가 나오기 전에 "오버엔지니어링"이라고 한 줄로 꺾을 수 있었거든요.
>
> 노션 확인은 제가 명령을 쳐서 돌리기도 하고, 루프로 몇 분마다 자동으로 돌게도 해 봤어요. 그런데 노션은 코드를 보기가 너무 어려웠습니다. diff도 없고 줄 단위 코멘트도 없어요. 노션을 오가느라 토큰도 많이 썼고요. 그래서 노션은 접고, 코드 안에서 바로 해결하는 쪽으로 돌아왔습니다.

**흐름 (발표자 참고, 질문 나오면)**

| 단계                    | 누가 | 무엇을                                                                |
| ----------------------- | ---- | --------------------------------------------------------------------- |
| 1. "새 할일 등록해줘 A" | AI   | 동작 단위로 세부 태스크 분해, 태스크마다 Given/When/Then 시나리오     |
| 2. 시나리오 승인        | 사람 | 피드백을 적으면 AI가 다시 씀. 괜찮으면 "시나리오검수" 체크            |
| 3. "노션 댓글 확인해줘" | AI   | 댓글 답글, 체크 감지, 구현 계획과 테스트 코드 작성, 실패(Red) 확인    |
| 4. 테스트와 계획 승인   | 사람 | 테스트 코드와 구현 계획을 보고 "개발구현방향" 체크 (또는 방향 피드백) |
| 5. 구현                 | AI   | 개발중, 승인된 테스트를 통과하도록 구현, 테스트중, 완료 댓글          |
| 6. 실패                 | AI   | 스스로 고쳐 재실행. 5번 실패하면 멈추고 검수요청                      |

**실제로 입력하는 말 (발표자 참고, 질문 나오면)**

한 태스크는 이렇게 진행된다.

1. `새 할일 등록해줘 [내용]` → AI가 큰 할일을 동작 단위 작은 태스크로 나누고 시나리오를 쓴다.
2. 사람이 "시나리오검수"를 체크한 뒤 `노션 댓글 확인해줘 [큰 할일 이름]` → AI가 테스트 코드와 구현 계획을 쓰고, 테스트가 실패하는 것까지 확인해 올린다.
3. 사람이 "개발구현방향"을 체크한 뒤 `노션 댓글 확인해줘 [큰 할일 이름]` → 그때 비로소 구현하고 "완료"로 바꾼다.

- 입력하는 말은 이 두 개뿐이다. 버튼이 아니라 Claude Code 터미널에 입력한다.
- 명령 한 번에 작은 태스크를 전부 보지만, 각 태스크는 체크된 만큼만 한 단계 간다. 그래서 작은 태스크가 한 번에 다 구현되지 않는다.
- 루프로 "노션 댓글 확인해줘"를 몇 분마다 돌리면 명령도 칠 필요가 없다. 나는 노션만 보면서 체크하고 댓글을 달았고, 코드는 AI가 짰다.
- 큰 할일 이름을 붙인다. 빼면 완료 아닌 큰 할일 전부가 대상이 된다.
- 발표 화면 예시: 큰 할일 "[워크플로우 테스트 3] 북마크 카드에 '읽은 지 N분 전' 표시" 아래 작은 태스크 4개가 단계별로 있다. 완료 2개(두 체크 다), 방향성 1개("읽은 시각 전용 필드", 시나리오검수만 체크, 테스트 코드 4개 Red 올라가 있음), 테스트 시나리오 1개("안 읽은 것만" 토글, 체크 없음). 방향성 태스크를 열어 "테스트 코드" 섹션을 보여 주며 "이걸 보고 체크하면 그때 구현한다"고 말한다.
- 실제 명령 실행은 노션 왕복으로 몇 분 걸리니 발표 중에는 화면만 보여 준다.

**가져갈 한 줄**: 승인 지점은 코드가 아니라 시나리오와 테스트에 두세요.

> 참고 (질문 대비, 대사에서 뺀 것): 원래 그림은 더 갔다. "이 기능은 이 파일에 있다"는 색인(PROJECT_INDEX.md)을 만들어 두고, 검수가 끝나면 AI가 그 색인으로 끝까지 자동 구현하게 할 생각이었다. 마지막 연결은 일부러 안 했다. 그 코드를 직접 보고 배우고 싶어서다. 노션 전에는 에이전트 여러 개를 팀처럼 돌리는 것도 해 보려 했는데 토큰이 너무 많이 나가서 접었다. 실제로 입력하는 말은 "새 할일 등록해줘"와 "노션 댓글 확인해줘" 두 개뿐이다. 다섯 번 실패하면 멈추고 사람한테 넘긴다.

> 참고 (질문 대비): 발표 준비하면서 에이전트한테 이 흐름을 세 번 다시 돌려 봤다(바탕화면 `노션-워크플로우-후기.md`). 앞의 두 번은 AI가 일한 시간만 치면 작은 태스크 하나에 5~7분, 노션 도구 호출 약 30번. 처음 돌렸을 때 막힌 건 AI가 아니라 문서였다(흐름 문서가 네 군데, 자동으로 읽히는 CLAUDE.md가 가장 오래된 버전이라 "검수라는 칸이 없다" 오류). 그래서 스킬 문서 하나로 모았다. "테스트 코드를 보고 승인" 단계는 이번 주에 문서로 되살렸고, 3차 사이클에서 새 흐름을 끝까지 돌렸다(약 9분, 노션 도구 호출 23번, 테스트 14개 먼저 작성하고 구현 전 실패 확인, 단 부정 확인 테스트 2개는 구현 전에도 통과).

**전환**: "그리고 노션에서 돌아와 보니, 코드 안에서 풀어야 할 문제가 하나 더 있었습니다. 세션이에요."

**1번 화면에서**

> 한 세션에서 개발도 하고, 보안도 보고, UX도 보다 보니 맥락이 섞이고, 길어지면 끊겼어요. 그래서 역할별로 에이전트를 나눴습니다. 코드 리뷰, 보안, UX, QA처럼 일마다 세션을 따로 쓰게 한 거예요. 에이전트 정의는 그냥 마크다운 파일입니다. 노션 이후로는 이렇게 세션을 나눠 관리하는 쪽으로만 쓰고 있어요. 팀에서 같이 쓸 때도 에이전트 관련해서는 md 파일로 "이런 일은 이 규칙"을 적어 두고 통일하려고 했습니다. 두 개만 보여 드릴게요. 하나는 만드는 쪽, 하나는 보는 쪽이에요.

**2번 화면(UI 에이전트)에서**

> 만드는 쪽입니다. 공통 컴포넌트를 만드는 에이전트예요. 로직은 공용 패키지에 스타일 없이 두고, 생김새는 앱에서 입히는 방식으로요. 파일 맨 위에 있는 규칙이 핵심인데, 어디에 만들지는 에이전트가 정하지 않고 제가 정합니다. 지정이 없으면 만들지 말고 먼저 물어보게 했어요.
>
> 피그마 시안이 있었다면 피그마를 MCP로 연결해서 디자인에서 바로 만들 수 있었을 텐데, 저는 시안이 없었습니다. 그래서 3월에 Input, Tag, Avatar 같은 기본 컴포넌트 몇 개를 만든 뒤로는 거의 쓰지 않았어요.

**돌려 본 이야기 (UI, 30초, 화면 전환 없이 말로)**

> 발표 준비하면서 다시 한 번 시켜 봤습니다. "둘 다 만들어줘, Badge 컴포넌트." 1분 만에 공용 패키지에 로직만 있는 파일과, 앱에 색을 입힌 파일을 기존 Tag 패턴 그대로 만들었어요.
>
> 재밌는 건 두 가지였어요. 하나, 공용 패키지에 새 컴포넌트를 쓰려면 내보내기 목록에 한 줄을 더해야 하는데, 제가 "다른 파일은 고치지 마"라고 했더니 그 한 줄을 안 고쳤어요. 대신 "이걸 먼저 물어봤어야 했다"고 보고에 적었고요. 둘, 규칙 문서에 "타입만 가져올 땐 import type을 써라"고 적어 뒀는데, 첫 줄부터 그걸 어겼습니다. 규칙 문서를 읽고도 어기는 거죠. 이 얘기는 조금 뒤에 다시 나옵니다.

**3번 화면(보안 에이전트)에서**

> 보는 쪽입니다. 보안은 두 관점으로 나눴어요. 하나는 방어자예요. 오와스프, 그러니까 웹 보안 취약점 기준표를 따라 "있어야 할 통제가 빠졌나"를 봅니다. 다른 하나는 공격자예요. "이걸로 무엇을 뺏을 수 있나"만 봅니다. 여기 공격자 표를 보시면 비로그인 사용자, 게스트, 로그인한 회원이 각각 무엇을 쥐고 들어오는지부터 정하고 시작해요.
>
> 둘은 서로의 결과를 보지 않습니다. 따로 돌린 다음에 종합하면, 둘 다 찾은 것과 한쪽만 찾은 것이 갈려요. 같은 API를 두 리뷰가 따로 봤을 때 둘 다 rate limit 부재를 지적했는데, 심각도는 서로 다르게 매겼습니다.
>
> 그리고 보안 에이전트는 언제 부를지가 문제인데, 이건 훅으로 알려 주게 했어요. git push를 하면 pre-push 훅이 바뀐 파일을 보고, API 라우트나 인증처럼 보안에 민감한 파일이 있으면 터미널에 경고를 띄웁니다. "보안 검토해줘" 명령어도 파일 이름까지 채워서 같이 보여 줘요. push를 막지는 않고 알려만 줍니다. 막는 건 시크릿이 들어갔을 때뿐이에요. 알려 주는 건 기계가, 판단은 에이전트가, 부르는 건 제가 하는 거죠.

**훅 경고를 보여 줄 때 (선택, 터미널)**: 실제 push 없이 같은 출력을 낸다. 시맨틱 검색 API를 바꾼 커밋 하나를 넣는다.

```bash
C=$(git log -1 --format=%H -- apps/web/src/app/api/semantic-search/route.ts); echo "refs/heads/x $C refs/heads/x $C~1" | node scripts/security/pre-push.mjs
```

나오는 결과: `[보안] 보안 민감 파일 1개가 바뀌었습니다. push는 계속합니다.`, 바뀐 파일과 이유, 그리고 `보안 검토해줘 apps/web/src/app/api/semantic-search/route.ts`. 민감 경로 목록은 `.github/security-sensitive-paths.json` 하나를 pre-push, PR 알림, 보안 에이전트가 같이 쓴다.

**돌려 본 이야기 (보안, 30초, 화면 전환 없이 말로)**

> 이것도 발표 전에 돌려 봤습니다. 이번 주에 회원은 하루 20번까지만 AI 검색을 쓰게 하는 코드를 넣었는데, 그 API를 "보안 검토해줘"로 보게 했어요. 1분 정도 걸렸습니다.
>
> 바로 제 코드의 구멍을 짚었어요. 오늘 몇 번 썼는지 세는 조회가 실패하면, 그 오류를 확인하지 않아서 0번으로 처리돼요. 그러면 제한이 풀립니다. 동시에 여러 번 보내면 다 통과할 수 있다는 것도요. 반대로 "남의 북마크를 볼 수 있나" 같은 건 DB 권한 정책까지 따라가서 막혀 있다고 확인해 줬고요. 무엇을 확인 못 했는지도 따로 적어 줬습니다.

**4번 화면(리뷰 보관소)에서**

## 4. 지금 하는 것: 코드 지도와 자동 시나리오 (4분)

**화면 순서**

1. 검증 지도 (바탕화면 `smart-bookmark-graph/qa-overlay.html`, 인터넷 필요): 어디가 비었나
2. 에이전트가 제안한 시나리오 파일 한 항목 (`qa-knowledge/proposals/2026-10-14-semantic-search-v2.json`): 빈 곳을 AI가 채운다
3. 장부 상태 (터미널 `node scripts/qa/qa.mjs status`, 또는 nightly 리포트 `qa-knowledge/reports/2026-10-14.md` 맨 위 요약 줄): 지금 상태를 장부가 안다
4. 테스트 작성 에이전트가 막히는 장면 (터미널, 아래 명령): 쓰는 쪽은 앱 코드를 못 고친다
5. 판정 실험 결과 (바탕화면 `판정-에이전트-실험/README.md`): 실패 원인을 가린다

4번은 에이전트를 실제로 부르지 않고 훅에 같은 입력을 넣어 바로 보여 준다(1초, 매번 같다):

```bash
echo '{"tool_name":"Edit","tool_input":{"file_path":"apps/web/src/app/api/semantic-search/route.ts"}}' | node .claude/hooks/qa-test-author-guard.mjs; echo "exit=$?"
```

나오는 결과: `qa-test-author 가드가 막음: apps/web/src/app/api/semantic-search/route.ts: 테스트 파일(*.test.ts, *.test.tsx), E2E spec(apps/web/e2e/*.spec.ts), 테스트 픽스처만 쓸 수 있다. 앱 코드는 고치지 않는다. 테스트가 실패하면 실패한 채로 보고한다`, `exit=2`. 종료 코드 2가 Claude Code에서 "막음"이다.

**1번 화면에서**

> 이건 이번 주에 만든 겁니다. 코드 전체를 그래프로 그리고, 그 위에 테스트 시나리오가 실제로 검증하는 파일을 칠했어요. 초록이 검증되는 곳, 회색이 아무 시나리오도 닿지 않는 곳입니다. 앱 코드의 절반 정도가 아직 회색이에요.
>
> 시나리오마다 "이 주장은 이 테스트가 검증하고, 이 코드에 연결된다"를 기록해 둡니다. 연결은 사람이 적지 않고 import 관계에서 기계가 뽑아요. 코드가 바뀌면 그 코드에 걸린 시나리오만 다시 확인 대상이 됩니다.

**2번 화면에서**

> 회색인 곳은 에이전트가 시나리오를 제안합니다. 시맨틱 검색으로 처음 돌려 봤는데, 17개를 제안했고 제가 14개를 승인했어요. 코드만 읽고 짚은 버그 후보 두 개는 테스트로 실제 재현됐습니다.
>
> 노션 때와 다른 점은 시나리오가 사용자 동작 단위고, 테스트도 그 동작을 확인한다는 거예요. 그래서 안쪽 코드를 리팩터링해도 테스트를 다시 쓸 일이 줄어요.

**3번 화면에서 (장부 상태)**

> 이건 장부의 지금 상태입니다. 시나리오마다 통과, 재검증 필요, 미검증, 보류가 붙고 이유가 같이 나와요. "검증 뒤 연결된 코드가 바뀜", "검증하는 테스트가 없음" 같은 거요. 제가 따로 챙기지 않아도 코드가 바뀌면 장부가 먼저 알고, 하루 세 번 도는 nightly가 재검증 필요인 것만 다시 돌립니다.

**4번 화면에서 (훅이 막는 장면)**

> 테스트는 에이전트가 씁니다. 그런데 테스트를 쓰는 AI가 앱 코드까지 고칠 수 있으면, 실패한 테스트를 앱을 고쳐서 통과시켜 버릴 수 있어요. 그러면 장부가 "통과"라고 거짓말을 하게 됩니다. 그래서 테스트를 쓰는 에이전트는 앱 코드를 못 고치게 훅으로 막았어요. 지금 이 에이전트가 앱 코드를 고치려고 하면, 보시는 것처럼 막히고 이유가 돌아갑니다. 아까 포맷 훅이 한 일을 뒤에서 고쳐 주는 훅이었다면, 이건 하려는 일을 앞에서 막는 훅이에요. 노션에서 약속으로 지키던 걸 여기서는 구조로 막은 겁니다.

**5번 화면에서 (판정)**

> 테스트가 실패하면 판정 에이전트가 앱 버그인지, 테스트가 틀린 건지, 환경 문제인지 가릅니다. 일부러 버그를 정상 커밋 사이에 숨겨서 돌려 봤는데, 원인은 8건 중 8건을 맞혔어요. 다만 이건 제가 문제를 낸 실험이라, 실제 데이터가 쌓이기 전에는 이슈를 자동으로 올리거나 코드를 고치게 하진 않을 겁니다.

**가져갈 한 줄**: 테스트를 쓰는 AI와 판정하는 AI를 나누고, 쓰는 쪽은 앱 코드를 못 건드리게 하세요.

> 참고 (질문 대비): 훅은 테스트를 쓰는 에이전트에만 걸린다. 그 에이전트를 지휘한 세션은 막히지 않는다(이번 주에 실제로 장부 경로 하나를 직접 고친 일이 있다). 3번 장부 상태는 브랜치마다 다르다. 발표 브랜치에는 발표용 변경이 있어서 "재검증 필요"가 많이 나온다. 그대로 보여 주고 "코드가 바뀌어서 그렇다"고 말하면 된다. nightly 리포트의 요약 줄은 "통과 13 · 미검증 4 · 보류 2 (시나리오 19개)"다. 판정 정확도는 사람 확인 10건 이상, 앱 버그 정확도 80% 이상이 되면 이슈 초안을 검토한다. 판정 실험 결과는 바탕화면 `판정-에이전트-실험/README.md`.

### 시간 부족할 때 (1분 30초, 화면 세 개)

3번 장부 상태와 5번 판정은 뺀다. 지도(1번), 제안 파일(2번), 훅이 막는 장면(4번)만 남긴다. 훅 장면은 빼지 않는다. 4부에서 "부탁이 아니라 구조로 막았다"를 실제로 보여 주는 유일한 장면이라, 이게 빠지면 3부까지의 이야기와 끊긴다.

"E2E 테스트 자동화"라고 부르지 않는다. 장부에 걸린 테스트는 단위, 통합, E2E가 섞여 있고, 핵심은 테스트 코드 생성이 아니라 장부가 먼저 알고 역할을 나눈 것이다. "테스트 시나리오 장부" 또는 "검증 지도"라고 부른다.

> 이번 주에 만들고 있는 겁니다. 코드 전체를 그래프로 그리고, 시나리오가 실제로 검증하는 파일을 초록으로 칠했어요. 회색은 아무 시나리오도 안 닿는 곳이고, 아직 절반쯤 됩니다.
>

질문 대비 두 개:

- "실제로 버그를 잡았나": 시맨틱 검색에서 17개 제안, 14개 승인, 코드만 읽고 짚은 버그 후보 2개가 테스트로 재현됐다.
- "이슈나 수정도 자동인가": 일부러 안 한다. 나이틀리는 보고만 하고 이슈를 만들지 않는다. 사람 확인 10건 이상, 앱 버그 판정 정확도 80% 이상이 쌓이면 이슈 초안부터 검토한다.

## 보안 검사 비교표

부록. 본문에서는 다루지 않고, 질문이 나오면 띄운다. 기능 하나가 배포되기까지의 흐름을 따라간다. 위에서 아래로 갈수록 느리고 판단이 필요하다.

**시점별 요약 (먼저 이것만 띄운다)**

| 시점              | 무엇이                                         | 막나          | 누가 만들었나            |
| ----------------- | ---------------------------------------------- | ------------- | ------------------------ |
| 커밋할 때         | (보안 검사 없음. 포맷만)                       | -             | 2월, 직접                |
| push할 때         | 시크릿 검사, 보안 민감 파일 경고, 의존성 경고  | 시크릿만 막음 | 이번 주                  |
| PR, main/dev push | CodeQL, 의존성 audit, 보안 리뷰 알림 코멘트    | 안 막음       | 이번 주                  |
| 매주 월요일       | CodeQL, 의존성 정기 검사. critical/high면 이슈 | 안 막음       | 이번 주                  |
| 사람이 부를 때    | 보안 리뷰 에이전트 둘 (방어자, 공격자)과 종합  | -             | 3월 직접, 이번 주 재작성 |

주의: 정기 검사는 매주다(한 달이 아니다). pre-commit에는 보안 검사가 없다.

**흐름**

```
① 코드 작성, 커밋
② git push            → 로컬 검사 (터미널)
③ GitHub가 push 받음   → push protection
④ dev로 PR 열기        → 알림 코멘트, CodeQL, 의존성 audit (PR 화면)
⑤ 알림이 달렸으면      → 내가 보안 리뷰 실행 (위험하면 심층 + 종합)
⑥ dev 머지
⑦ dev → main PR        → "배포 전" 알림, 심층 리뷰와 종합 확인
⑧ main 머지, 배포
⑨ 매주 월요일          → 정기 검사, 문제 있으면 이슈 (코드를 안 건드려도)
```

②~④와 ⑨는 자동이다. ⑤와 ⑦의 리뷰만 사람이 판단해서 부른다.

**비교표** (시간은 2026-10-14 실측. 재지 못한 것은 표시)

정기 검사(⑨)는 main에 머지된 뒤부터 돈다. GitHub 정기 실행은 기본 브랜치의 워크플로우만 돌리기 때문이다.

**한 줄로 보면**

- 몇 초: push 전 검사. 매번 돌고, 시크릿만 막는다
- 1~2분: PR 검사. 매번 돌고, 보안 검사는 막지 않고 알려만 준다. 문서 경로 검사만 틀리면 막는다
- 2~3분: AI 리뷰. 사람이 부를 때만 돈다
- 매주: 코드를 안 건드려도 새로 공개된 취약점을 잡아서 이슈로 알려 준다

**언제 무엇을 보나**

- 커밋, push: 결정론 검사만 자동으로 돈다. AI 리뷰는 돌지 않는다
- feature → dev PR에 알림이 달렸을 때: 기본 리뷰. 인증, RLS, 토큰이면 심층 리뷰와 종합까지
- dev → main PR (배포 전): 알림에 "배포 전" 문구가 붙는다. 심층 리뷰와 종합을 확인한다. E2E를 main PR에서만 돌리는 것과 같은 자리다
- PR 템플릿 체크리스트에 위 확인 항목이 들어 있다. 막지는 않는다

**실측 (2026-10-14)**

- pre-push: 이 체계를 넣은 커밋 기준 2초. 가짜 GitHub 토큰을 넣은 커밋은 막히고 값은 가려짐
- CodeQL 첫 실행: 새로 쓴 워크플로우에서 외부 액션을 태그로 부르는 문제 1건을 찾음. 같은 패턴 6곳을 커밋 SHA로 고정
- 의존성 audit: prod에 critical 2, high 31 (next 16.1.6). 막지 않고 리포트와 이슈로 알림
- 같은 익스텐션 저장 API를 두 리뷰가 따로 봄: 둘 다 rate limit 부재, DNS rebinding SSRF, 전역 tags 테이블을 지적. 심각도 판단은 엇갈림 (rate limit을 기본은 High, 공격자는 Medium)
- 문서 경로 검사 (PR #124): 일부러 옛 경로를 넣고 push하자 Lint & Typecheck 실패, 머지 상태 BLOCKED. 코멘트 표에 `PROJECT_INDEX.md:220`의 없는 경로가 나옴. 되돌리자 통과하고 같은 코멘트가 "해결됨"으로 갱신 (코멘트 1개 유지)

| 알림 코멘트를 왜 리뷰 실행으로 안 바꿨나?                 | 보안 민감 파일은 자주 바뀐다(API 라우트만 17개). 매번 AI 리뷰를 돌리면 느리고 비싸고 노이즈가 쌓여서 결국 안 읽게 된다. 알림은 비용이 0에 가깝고, 돌릴지 말지는 PR 내용을 아는 사람이 판단한다                                                                                                                                                                                                                                                                      |
| QA 에이전트가 놓치면?                                     | 핵심 흐름은 에이전트가 아니라 테스트가 지킨다. AI 파이프라인 상태 전환, 실패/재시도, 비회원 한도는 `src/__tests__/`의 통합 테스트와 `e2e/pipeline-failure.spec.ts`, `bookmark-save.spec.ts`로 고정돼 CI에서 매번 돈다. QA 에이전트는 그 위에 얹는 보조다                                                                                                                                                                                                            |
| 시맨틱 검색이 맞게 나오는지는 어떻게 아나?                | 지금은 모른다. 기준값 0.65/0.8은 감으로 정했다(`docs/decisions/029`). 다음 작업은 정답 세트(북마크 + 검색어 + 기대 결과)로 Recall@5 같은 지표를 재는 오프라인 평가다. 실제 API를 불러 비용이 들고 모델 업데이트로 값이 흔들릴 수 있어서 CI 게이트가 아니라 모델·기준값·임베딩 입력을 바꿀 때 돌린다. 반면 0.8 경계로 나누는 로직, 화면 표시, 실패 피드백은 결정론이라 일반 테스트로 막는다                                                                          |
| 에이전트나 규칙 문서는 어떻게 관리하나? 문서도 썩지 않나? | 썩는다. 발표 준비 중 에이전트, 스킬, 명령, CLAUDE.md에서 옛 경로 21곳을 손으로 찾았고, 경로 기준인 PROJECT_INDEX.md에도 틀린 항목이 있었다. 그래서 파일 경로 기준을 PROJECT_INDEX.md 한 곳으로 모으고, 다른 문서는 이름만 쓴다. 문서에 적힌 경로가 git에 없으면 CI(Lint & Typecheck)가 PR을 막고 코멘트로 알려 준다. 사람이 기억할 걸 결정론 검사로 바꾼 것이라 오늘 발표 원칙과 같다. 한계: 적힌 경로가 있는지만 본다. 새 파일이 PROJECT_INDEX에 빠진 건 못 잡는다 |
| 비용은?                                                   | 부를 때만 돌아서 크지 않다. (실제 수치는 없으면 "측정하지 않았다"고 말한다)                                                                                                                                                                                                                                                                                                                                                                                         |
| QA 에이전트는 어디에 쓰나?                                | 애니메이션 끊김, 작은 모바일 버튼처럼 테스트로 만들기 애매한 완성도 문제를 볼 때만 부른다. 진짜 버그로 확인된 건 테스트로 남긴다. 다만 헤더 QA로 남긴 회귀 테스트(`qa-header.spec.ts`)는 로그인 계정이 필요해서 지금은 건너뛰어진다. 돈다고 말하지 않는다                                                                                                                                                                                                           |

## 부록: 포맷 훅과 보안 검사 (예전 3절, 질문 나오면)

**화면**: `.claude/hooks/format.mjs` 상단 주석의 "결정론 경계" 단락 → `apps/web/src/shared/lib/formatDemo.ts` 열기

**주석을 보여주며**

> 기준은 이 주석에 적어 뒀습니다. 빠르고 객관적인 건 강제한다. 느리고 판단이 필요한 건 강제하지 않는다.
>
> 포맷은 정답이 정해져 있죠. 그러니 AI한테 "포맷 맞춰줘"라고 부탁하지 않고 훅으로 강제합니다.

**formatDemo.ts를 보여주며**

> 이 파일은 일부러 엉망으로 둔 겁니다. 들여쓰기도 제각각이고 세미콜론도 없어요.

**Claude에 입력**

```
formatDemo.ts의 formatDemoTags에서 구분자를 ", "에서 " "로 바꿔줘
```

**기다리는 동안 (훅이 약 8초 걸린다)**

> 저는 한 줄만 고쳐 달라고 했고, Claude도 한 줄만 고칩니다. 그런데 저장된 직후에 훅이 prettier와 eslint --fix를 돌려요.

**diff가 바뀌면**

> 파일 전체가 정리됐습니다. 세미콜론, 큰따옴표, 들여쓰기까지요. Claude가 포맷 규칙을 기억하든 말든 상관없습니다. 이게 "부탁"과 "강제"의 차이예요.
>
> 참고로 이 훅은 실패해도 편집을 막지 않게 해 뒀습니다. 포맷 때문에 작업이 멈추면 그게 더 큰 마찰이라서요.

**이어서** 바탕화면의 `security-nudge-pr-comment.png` (실제 PR #122에 달린 알림 코멘트)

> 그런데 "사람이 부를 때만"에는 구멍이 있습니다. 사람이 까먹어요. 저도 보안 에이전트는 3월에 만들고, 3월과 7월 두 번밖에 안 돌렸습니다.
>
> 그래서 경계를 한 번 더 쪼갰습니다. "보안 민감 파일이 바뀌었나"는 경로만 보면 되니까 객관적이죠. 이건 CI가 자동으로 감지해서 PR에 코멘트를 답니다. 어떤 파일이 왜 민감한지, 로컬에서 뭐라고 치면 되는지까지요. 하지만 "실제로 취약한가"는 판단이라, 리뷰를 돌릴지는 여전히 제가 정합니다. CI를 막지도 않아요.
>
> 과거 커밋에 돌려 보면, 7월 보안 수정 커밋은 12개 파일 중 9개, 3월 인증 수정은 7개 중 5개, RLS 수정은 3개 중 3개를 잡습니다. 문서만 바꾼 PR에서는 아무 말도 안 하고요.

**이어서** 이 문서 맨 아래 "보안 검사 비교표" (50초)

> 저는 보안 전문가가 아닙니다. 그래서 두 가지를 바꿨어요.
>
> 하나는 일관성입니다. AI 리뷰는 돌릴 때마다 결과가 달라서, 매번 같아야 하는 검사는 규칙 기반 도구에 맡겼습니다. push 전에는 로컬에서 시크릿을 검사해서 막고, PR과 main, dev push마다 CodeQL과 의존성 검사가 돕니다. 처음 돌려 보니 Next.js 버전에 알려진 high 취약점이 여러 개 나왔어요. 코드를 읽는 리뷰 에이전트로는 잡을 수 없는 종류예요.
>
> 다른 하나는 전문 지식입니다. 제가 만든 체크리스트 대신 OWASP 기준을 담은 공개 스킬을 붙였고, 보안 감사 회사 Trail of Bits의 공격자 모델링 방법으로 심층 리뷰어를 하나 더 만들었습니다. 둘은 서로의 결과를 모르게 따로 돌고, 종합은 제가 요청할 때 개발 세션이 합니다. 둘 다 찾은 건 먼저 고치고, 한쪽만 찾은 건 근거를 확인합니다.
>
> 그리고 알림이 어디로 오는지도 정했습니다. push 전 검사는 터미널에, PR 검사는 PR 코멘트로 GitHub 알림이 옵니다. 문제는 매주 도는 정기 검사였어요. 실패하지 않으면 아무도 모릅니다. 그래서 critical이나 high가 있으면 이슈를 하나 만들고, 해소되면 알아서 닫히게 했습니다. 이것도 막지는 않고 알려주기만 합니다.
>
> 걸리는 시간으로 보면 push 전 검사는 2초, PR 검사는 1~2분, AI 리뷰는 부를 때만 2~3분입니다. 빠른 건 매번, 느린 건 필요할 때만 돌게 나눈 거예요.

**강조할 문장**: "감지는 결정론으로, 실행은 사람이." 같은 리뷰 하나 안에서도 경계를 나눌 수 있다는 것.

**전환**: "같은 문제를 두 방식으로 잡으면 이 경계가 더 잘 보입니다."
