## 1. 에이전트를 페르소나로 나누고, 리뷰는 파일로 (3분)

**화면**: 파일 트리에서 `.claude/` 펼치기 → `agents/`, `commands/`, `skills/` → `.claude/project/reviews/` 폴더 → `CLAUDE.md`의 "리뷰 결과 보관소" 표

> 처음 문제는 세션이었습니다. 한 세션에서 개발도 하고, 보안도 보고, UX도 보다 보니 맥락이 섞이고, 길어지면 중간에 끊겼어요. 그래서 역할별로 에이전트를 나눴습니다. 코드 리뷰, 보안 리뷰, UX, QA 같은 페르소나예요.
>
> 이 에이전트들은 서로의 결과를 보지 않습니다. 공유하는 건 CLAUDE.md와 기획서뿐이에요. 결과는 이 폴더에 날짜별 파일로 남기고, 개발 세션이 필요한 것만 골라 읽습니다.
>
> 이렇게 한 이유가 두 가지예요.
> 하나는 컨텍스트 오염입니다. 보안 리뷰를 본 상태로 UX 리뷰를 하면 UX 리뷰도 보안 쪽으로 쏠립니다.
> 다른 하나는 제가 겪은 건데, 리뷰를 실시간으로 붙이면 개발이 리뷰에 끌려갑니다. 제가 시킨 것 말고 리뷰에서 지적된 다른 파일까지 같이 고치거나, "Critical부터 먼저 해결하겠다"면서 시킨 작업을 뒤로 미뤘어요. 리뷰가 틀린 건 아닌데, 제가 정한 순서가 아니었습니다. 제 통제가 어려워지더라고요.
>
> 그래서 리뷰는 제가 필요할 때 부르고, 결과는 파일로 쌓아 두고, 반영할 것도 제가 고릅니다.

**전환**: "맥락은 이렇게 나눴는데, 그다음 문제는 승인이었습니다. AI가 어디까지 혼자 가도 되느냐요."

## 2. 노션 검수 파이프라인 (4분)

**화면 순서**

1. `.claude/skills/task-pipeline/SKILL.md`의 "2-2. 체크박스 감지와 단계 진행" 표
2. 노션 세부 태스크 DB 뷰 (사이드바 접고 링크로 직접 열기)
3. 완료 사례: 「잘못된 URL 입력 시 모달 내 에러 메시지 표시 확인」
4. 이번 주 테스트 사이클: 툴팁 태스크의 댓글 스레드 (결정 질문과 `[AI]` 답글)

**1번 화면에서**

> 노션에 할일을 하나 등록하면 AI가 태스크를 동작 단위로 나누고, 태스크마다 Given/When/Then 테스트 시나리오를 씁니다. 제가 "시나리오검수"를 체크하면 AI가 관련 코드를 읽고 구현 계획을 쓰고, "개발구현방향"을 체크하면 테스트를 먼저 쓰고 구현합니다. 테스트가 5번 넘게 실패하면 멈추고 저한테 넘기고요.
>
> 사람은 체크박스 두 번만 누르고, 그 사이를 AI가 시나리오, 계획, 테스트, 구현으로 채웁니다. 코드를 승인하는 게 아니라 시나리오와 계획을 승인하는 거예요.

**흐름 (발표자 참고, 1번 화면과 같이 본다)**

| 단계                    | 누가 | 무엇을                                                                                                    |
| ----------------------- | ---- | --------------------------------------------------------------------------------------------------------- |
| 1. "새 할일 등록해줘 A" | AI   | 큰 할일 생성, 화면에서 확인 가능한 동작 단위로 세부 태스크 분해, 태스크마다 Given/When/Then 시나리오 작성 |
| 2. 시나리오 승인        | 사람 | 시나리오 피드백을 적으면 AI가 다시 씀. 괜찮으면 "시나리오검수" 체크                                       |
| 3. "노션 댓글 확인해줘" | AI   | 댓글에 답글, 체크 감지, 관련 코드를 읽고 구현 계획 작성                                                   |
| 4. 구현 계획 승인       | 사람 | "개발구현방향" 체크 (또는 방향 피드백)                                                                    |
| 5. 구현                 | AI   | 개발중 → 테스트 먼저 작성(실패 확인) → 구현 → 테스트중 → 완료 댓글                                        |
| 6. 실패                 | AI   | 스스로 고쳐 다시 실행. 5번 실패하면 멈추고 검수요청, 실패 로그를 댓글로                                   |

**3번 화면(완료 사례)에서**

> 실제로 돈 사례입니다. 시나리오 네 케이스, 관련 코드 수집, 구현 계획까지 한 페이지에 쌓였고요. 여기 보시면 제가 "RHF 쓰는 건 오버엔지니어링"이라고 방향을 꺾은 피드백도 남아 있습니다. 이 관문은 실제로 쓸모가 있었어요.

**4번 화면(이번 주 테스트 사이클)에서**

> 발표 준비하면서 이걸 두 번 다시 돌려 봤습니다. 작은 UI 태스크 하나가 등록부터 완료까지 5~7분, 노션 도구 호출 30번 안팎이었어요. 여기 보시면 "툴팁에 시간까지 보여줄까요?" 같은 결정 질문에는 AI가 혼자 정하지 않고 선택지만 내고 기다립니다.
>
> 그런데 처음 돌렸을 때 막힌 곳은 AI가 아니라 문서였습니다. 흐름을 설명하는 문서가 네 군데로 갈라져 있었고, 자동으로 읽히는 CLAUDE.md가 가장 오래된 버전이라 "검수라는 컬럼이 없다"는 오류가 났어요. 그래서 흐름을 스킬 문서 하나로 모으고, 나머지는 거기를 가리키게만 했습니다.

**한계 (30초)**

> 해 보니 한계도 분명했습니다.
> 하나, 태스크를 잘게 나누니 시나리오는 화면 동작인데 테스트는 그 안쪽 함수를 보는 유닛 테스트가 됐습니다. 스펙이 바뀔 때마다 시나리오와 유닛 테스트를 같이 고쳐야 했어요. 1인 개발에서는 이 유지비가 컸습니다.
> 둘, 에이전트와 제가 같은 노션 계정을 써서, 체크박스를 누가 눌렀는지 노션에서는 구분이 안 됩니다. 승인 관문이 구조가 아니라 약속으로 지켜지고 있었어요.

> 참고 (질문 대비): 두 사이클 후기는 바탕화면 `노션-워크플로우-후기.md`. 두 사이클 모두 테스트용 태스크에 한해 에이전트가 체크박스를 대신 눌렀다. 사람 검수가 들어간 사이클이라고 말하지 않는다.

**전환**: "두 번째 한계, 규칙이 약속으로만 지켜진다는 게 다음 이야기로 이어집니다."

## 3. 규칙은 구조로: lint:fsd vs fsd-checker (2분)

**화면**: `apps/web/src/entities/bookmark/lib/countByQuery.ts` 4번째 줄

> 이 프로젝트는 FSD 구조라서 하위 레이어가 상위 레이어를 import하면 안 됩니다. 이 파일은 entities인데 features를 import하고 있죠. 일부러 심은 위반입니다.

**터미널 (명령 A)**

```
pnpm --filter @smart-bookmark/web lint:fsd
```

> ESLint 규칙으로 만든 lint:fsd예요. 정확히 이 줄을 잡고, 몇 번을 돌려도 같은 결과가 나옵니다. CI에 게이트로 걸려 있어서 이게 있으면 머지가 안 됩니다.

**Claude에 입력 (명령 B, 시간 있으면)**

```
FSD 레이어 위반 찾아줘
```

> 처음엔 이걸 fsd-checker 에이전트한테 시켰습니다. 같은 위반을 잡지만, 매번 조금씩 다르게 봅니다. 그래서 방향 규칙처럼 기계적으로 판단할 수 있는 건 규칙으로 내리고, 에이전트에는 판단이 필요한 것만 남겼습니다.
>
> 문서도 마찬가지예요. 문서에 적힌 파일 경로가 실제로 없으면 PR을 막는 검사를 넣었습니다. 에이전트한테 "경로 맞는지 봐줘"라고 부탁하지 않습니다.

**주의**: 에이전트 출력은 실행마다 조금씩 다르다. 결과가 다르게 나와도 "그래서 게이트에 안 넣었다"로 오히려 연결된다.

**전환**: "테스트도 같은 기준으로 남았습니다."

## 4. 사용자 동작 테스트와 QA 에이전트 (2분)

**화면**: `apps/web/e2e/pipeline-failure.spec.ts` 9~37줄

> 크롤링 API가 실패하도록 mock하고, 사용자 눈에 보이는 에러 문구와 재시도 버튼만 확인하는 테스트입니다. 스토어가 어떻게 생겼는지, 서비스가 뭘 호출하는지는 보지 않아요.

**터미널 (시간 되면)**

```
pnpm --filter @smart-bookmark/web exec playwright test e2e/pipeline-failure.spec.ts -g "크롤링 실패 → 에러 카드" --project=chromium
```

> 이 테스트는 내부를 리팩터링해도 깨지지 않습니다. 노션 파이프라인의 유닛 시나리오와 정반대예요. 사용자가 보는 동작이 그대로면 테스트도 그대로입니다.
>
> QA 에이전트는 이런 테스트로 잡기 애매한 것, 애니메이션이 끊기거나 모바일 버튼이 작은 것 같은 완성도 문제를 볼 때만 부릅니다. 그중 진짜 버그로 확인된 건 테스트로 남겨요. 헤더 QA에서 찾은 로그아웃 중복 클릭 버그가 지금 회귀 테스트로 남아 있습니다.

**전환**: "그런데 이런 테스트를 사람이 하나하나 쓰고 관리하는 데도 한계가 있었습니다. 그래서 요즘 하고 있는 게 이겁니다."

## 5. 요즘 방향: 코드 지도와 자동 시나리오 (3.5분)

**화면 순서**

1. 바탕화면 `smart-bookmark-graph/qa-overlay.html` (검증 지도)
2. 터미널 `node scripts/qa/qa.mjs status`
3. `qa-knowledge/proposals/2026-10-14-semantic-search-v2.json` (에이전트 제안) 한 항목
4. 바탕화면 `판정-에이전트-실험/README.md`의 2차 결과 표

**1번 화면에서**

> 이건 코드 전체 지도입니다. 그래피파이로 코드 구조를 그래프로 만들고, 그 위에 테스트 시나리오가 실제로 검증하는 파일을 칠했어요. 초록이 검증되는 곳, 회색이 아무 시나리오도 닿지 않는 곳입니다. 앱 파일 기준으로 절반 정도가 아직 회색이에요.

**2번 화면에서**

> 시나리오마다 "이 주장은 이 테스트가 검증하고, 이 코드에 연결된다"를 장부로 들고 있습니다. 연결은 사람이 적지 않고 import 관계에서 기계가 뽑아요. 코드가 바뀌면 그 코드에 연결된 시나리오만 "재검증 필요"가 되고, 매일 밤 그것만 다시 돌립니다.

**3번 화면에서**

> 회색인 곳은 에이전트가 시나리오를 제안합니다. 시맨틱 검색으로 처음 돌려 봤는데, 17개를 제안했고 제가 14개를 승인했어요. 코드만 읽고 찾은 버그 후보 두 개가 테스트로 실제 재현됐고, 그날 고친 버그가 6건입니다.
>
> 노션 때와 다른 점은 시나리오가 사용자 동작 단위이고, 테스트가 그 동작을 확인한다는 거예요. 그리고 테스트를 쓰는 에이전트는 앱 코드를 못 고치게 훅으로 막았습니다. 노션에서 배운 대로, 규칙을 약속이 아니라 구조로 걸었어요.

**4번 화면에서**

> 테스트가 실패하면 판정 에이전트가 앱 버그인지, 테스트가 틀린 건지, 환경 문제인지 가릅니다. 일부러 버그를 정상 커밋 사이에 섞어 넣고 돌려 봤는데, 원인은 8건 중 8건을 맞혔고 분류는 7건이 맞았습니다.
>
> 다만 이건 제가 문제를 낸 실험입니다. 실제 나이틀리에서 판정이 얼마나 맞는지 쌓이기 전에는 이슈를 자동으로 올리거나 코드를 고치게 하지 않으려고요.

> 참고 (질문 대비): 지도는 import 기반이라 문자열로 부르는 API, 클릭으로 넘어가는 페이지는 일부만 잡는다. 판정 정확도 기준은 "사람 확인 10건 이상, 앱 버그 정확도 80% 이상"이 되면 이슈 초안을 검토한다.

## 보안 검사 비교표

발표 3번 섹션에서 띄우는 표. 기능 하나가 배포되기까지의 흐름을 따라간다. 위에서 아래로 갈수록 느리고 판단이 필요하다.

**흐름**

```
① 코드 작성, 커밋
② git push            → 로컬 검사 (터미널)
③ GitHub가 push 받음   → push protection
④ dev로 PR 열기        → 알림 코멘트, CodeQL, 의존성 audit (PR 화면)
⑤ 알림이 달렸으면      → 내가 보안 리뷰 실행 (위험하면 심층 + 종합)
⑥ dev 머지
⑦ dev → main PR        → "배포 전" 알림, 심층 리뷰와 종합 확인
⑧ main 머지, 배포
⑨ 매주 월요일          → 정기 검사, 문제 있으면 이슈 (코드를 안 건드려도)
```

②~④와 ⑨는 자동이다. ⑤와 ⑦의 리뷰만 사람이 판단해서 부른다.

정기 검사(⑨)는 main에 머지된 뒤부터 돈다. GitHub 정기 실행은 기본 브랜치의 워크플로우만 돌리기 때문이다.

**한 줄로 보면**

- 몇 초: push 전 검사. 매번 돌고, 시크릿만 막는다
- 1~2분: PR 검사. 매번 돌고, 보안 검사는 막지 않고 알려만 준다. 문서 경로 검사만 틀리면 막는다
- 2~3분: AI 리뷰. 사람이 부를 때만 돈다
- 매주: 코드를 안 건드려도 새로 공개된 취약점을 잡아서 이슈로 알려 준다

**언제 무엇을 보나**

- 커밋, push: 결정론 검사만 자동으로 돈다. AI 리뷰는 돌지 않는다
- feature → dev PR에 알림이 달렸을 때: 기본 리뷰. 인증, RLS, 토큰이면 심층 리뷰와 종합까지
- dev → main PR (배포 전): 알림에 "배포 전" 문구가 붙는다. 심층 리뷰와 종합을 확인한다. E2E를 main PR에서만 돌리는 것과 같은 자리다
- PR 템플릿 체크리스트에 위 확인 항목이 들어 있다. 막지는 않는다

**실측 (2026-10-14)**

- pre-push: 이 체계를 넣은 커밋 기준 2초. 가짜 GitHub 토큰을 넣은 커밋은 막히고 값은 가려짐
- CodeQL 첫 실행: 새로 쓴 워크플로우에서 외부 액션을 태그로 부르는 문제 1건을 찾음. 같은 패턴 6곳을 커밋 SHA로 고정
- 의존성 audit: prod에 critical 2, high 31 (next 16.1.6). 막지 않고 리포트와 이슈로 알림
- 같은 익스텐션 저장 API를 두 리뷰가 따로 봄: 둘 다 rate limit 부재, DNS rebinding SSRF, 전역 tags 테이블을 지적. 심각도 판단은 엇갈림 (rate limit을 기본은 High, 공격자는 Medium)
- 문서 경로 검사 (PR #124): 일부러 옛 경로를 넣고 push하자 Lint & Typecheck 실패, 머지 상태 BLOCKED. 코멘트 표에 `PROJECT_INDEX.md:220`의 없는 경로가 나옴. 되돌리자 통과하고 같은 코멘트가 "해결됨"으로 갱신 (코멘트 1개 유지)

QA 에이전트는 그 위에 얹는 보조다                                                                                                                                                                                                            |
| 시맨틱 검색이 맞게 나오는지는 어떻게 아나?                | 지금은 모른다. 기준값 0.65/0.8은 감으로 정했다(`docs/decisions/029`). 다음 작업은 정답 세트(북마크 + 검색어 + 기대 결과)로 Recall@5 같은 지표를 재는 오프라인 평가다. 실제 API를 불러 비용이 들고 모델 업데이트로 값이 흔들릴 수 있어서 CI 게이트가 아니라 모델·기준값·임베딩 입력을 바꿀 때 돌린다. 반면 0.8 경계로 나누는 로직, 화면 표시, 실패 피드백은 결정론이라 일반 테스트로 막는다                                                                          |
| 에이전트나 규칙 문서는 어떻게 관리하나? 문서도 썩지 않나? | 썩는다. 발표 준비 중 에이전트, 스킬, 명령, CLAUDE.md에서 옛 경로 21곳을 손으로 찾았고, 경로 기준인 PROJECT_INDEX.md에도 틀린 항목이 있었다. 그래서 파일 경로 기준을 PROJECT_INDEX.md 한 곳으로 모으고, 다른 문서는 이름만 쓴다. 문서에 적힌 경로가 git에 없으면 CI(Lint & Typecheck)가 PR을 막고 코멘트로 알려 준다. 사람이 기억할 걸 결정론 검사로 바꾼 것이라 오늘 발표 원칙과 같다. 한계: 적힌 경로가 있는지만 본다. 새 파일이 PROJECT_INDEX에 빠진 건 못 잡는다 |
| 비용은?                                                   | 온디맨드라 크지 않다. ## 부록: 포맷 훅과 보안 검사 (예전 3절, 질문 나오면)

**화면**: `.claude/hooks/format.mjs` 상단 주석의 "결정론 경계" 단락 → `apps/web/src/shared/lib/formatDemo.ts` 열기

**주석을 보여주며**

> 기준은 이 주석에 적어 뒀습니다. 빠르고 객관적인 건 강제한다. 느리고 판단이 필요한 건 강제하지 않는다.
>
> 포맷은 정답이 정해져 있죠. 그러니 AI한테 "포맷 맞춰줘"라고 부탁하지 않고 훅으로 강제합니다.

**formatDemo.ts를 보여주며**

> 이 파일은 일부러 엉망으로 둔 겁니다. 들여쓰기도 제각각이고 세미콜론도 없어요.

**Claude에 입력**

```
formatDemo.ts의 formatDemoTags에서 구분자를 ", "에서 " "로 바꿔줘
```

**기다리는 동안 (훅이 약 8초 걸린다)**

> 저는 한 줄만 고쳐 달라고 했고, Claude도 한 줄만 고칩니다. 그런데 저장된 직후에 훅이 prettier와 eslint --fix를 돌려요.

**diff가 바뀌면**

> 파일 전체가 정리됐습니다. 세미콜론, 큰따옴표, 들여쓰기까지요. Claude가 포맷 규칙을 기억하든 말든 상관없습니다. 이게 "부탁"과 "강제"의 차이예요.
>
> 참고로 이 훅은 실패해도 편집을 막지 않게 해 뒀습니다. 포맷 때문에 작업이 멈추면 그게 더 큰 마찰이라서요.

**(시간 여유 있으면)** `.github/workflows/claude-review.yml` 상단 주석:

> 반대로 AI 코드리뷰는 CI에 강제로 넣지 않았습니다. 느리고, 돌릴 때마다 결과가 다르거든요. PR에 `ai-review` 라벨을 달거나 `@claude`라고 부를 때만 돕니다.

**이어서** 바탕화면의 `security-nudge-pr-comment.png` (실제 PR #122에 달린 알림 코멘트)

> 그런데 "사람이 부를 때만"에는 구멍이 있습니다. 사람이 까먹어요. 저도 보안 에이전트는 3월에 만들고, 3월과 7월 두 번밖에 안 돌렸습니다.
>
> 그래서 경계를 한 번 더 쪼갰습니다. "보안 민감 파일이 바뀌었나"는 경로만 보면 되니까 객관적이죠. 이건 CI가 자동으로 감지해서 PR에 코멘트를 답니다. 어떤 파일이 왜 민감한지, 로컬에서 뭐라고 치면 되는지까지요. 하지만 "실제로 취약한가"는 판단이라, 리뷰를 돌릴지는 여전히 제가 정합니다. CI를 막지도 않아요.
>
> 과거 커밋에 돌려 보면, 7월 보안 수정 커밋은 12개 파일 중 9개, 3월 인증 수정은 7개 중 5개, RLS 수정은 3개 중 3개를 잡습니다. 문서만 바꾼 PR에서는 아무 말도 안 하고요.

**이어서** 이 문서 맨 아래 "보안 검사 비교표" (50초)

> 저는 보안 전문가가 아닙니다. 그래서 두 가지를 바꿨어요.
>
> 하나는 일관성입니다. AI 리뷰는 돌릴 때마다 결과가 달라서, 매번 같아야 하는 검사는 규칙 기반 도구에 맡겼습니다. push 전에는 로컬에서 시크릿을 검사해서 막고, PR과 main, dev push마다 CodeQL과 의존성 검사가 돕니다. 처음 돌려 보니 Next.js 버전에 알려진 high 취약점이 여러 개 나왔어요. 코드를 읽는 리뷰 에이전트로는 잡을 수 없는 종류예요.
>
> 다른 하나는 전문 지식입니다. 제가 만든 체크리스트 대신 OWASP 기준을 담은 공개 스킬을 붙였고, 보안 감사 회사 Trail of Bits의 공격자 모델링 방법으로 심층 리뷰어를 하나 더 만들었습니다. 둘은 서로의 결과를 모르게 따로 돌고, 종합은 제가 요청할 때 개발 세션이 합니다. 둘 다 찾은 건 먼저 고치고, 한쪽만 찾은 건 근거를 확인합니다.
>
> 그리고 알림이 어디로 오는지도 정했습니다. push 전 검사는 터미널에, PR 검사는 PR 코멘트로 GitHub 알림이 옵니다. 문제는 매주 도는 정기 검사였어요. 실패하지 않으면 아무도 모릅니다. 그래서 critical이나 high가 있으면 이슈를 하나 만들고, 해소되면 알아서 닫히게 했습니다. 이것도 막지는 않고 알려주기만 합니다.
>
> 걸리는 시간으로 보면 push 전 검사는 2초, PR 검사는 1~2분, AI 리뷰는 부를 때만 2~3분입니다. 빠른 건 매번, 느린 건 필요할 때만 돌게 나눈 거예요.

**강조할 문장**: "감지는 결정론으로, 실행은 사람이." 같은 리뷰 하나 안에서도 경계를 나눌 수 있다는 것.

**전환**: "같은 문제를 두 방식으로 잡으면 이 경계가 더 잘 보입니다."
