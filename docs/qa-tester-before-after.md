# QA 방식: 이전과 지금

> 발표, 공유용 요약. "이전엔 이랬다 → 그래서 지금은 이렇게 하는 중이다." 지금 방식은 1단계까지 만든 진행 중 상태다.
> 자세한 사용법과 한계는 [qa-tester.md](qa-tester.md).

## 한 줄로

**이전:** 사람이 시나리오와 체크리스트를 쓰고, 테스트는 매번 전부 돌리고, QA 결과는 그때그때 보고서로 끝났다.
**지금:** 테스트가 검증한 사실을 근거와 함께 장부에 쌓고, 코드가 바뀌면 그 코드에 걸린 사실만 다시 확인한다.

## 비교

| ------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |

## 실제로 확인한 것

**1. 바뀐 것만 다시 본다.** `validateSsrf.ts`에 주석 한 줄을 넣자 통과 8개 중 2개만 재검증 필요가 됐다. SSRF 시나리오(직접)와 파이프라인 실패 시나리오(크롤러가 그 파일을 씀)다. 되돌리자 다시 통과로 돌아왔다. 이전 방식이었다면 테스트 226개를 전부 돌리고, 어떤 주장이 흔들렸는지는 알 수 없었다.

**2. 장부가 숨은 사실을 드러냈다.**

- 기획서에 "완료"로 적힌 컬렉션 기능이 실제로는 미완성인데 화면에 노출돼 있었다. 테스트는 0개. 장부에 주장을 쓰다가 기획서, 화면, 테스트가 서로 다른 말을 하는 걸 발견했고, 기능을 숨겼다 (PR #126)
- E2E가 API를 전부 mock하고 있어서, 크롤러나 AI 라우트를 고쳐도 E2E 시나리오는 아무 영향을 받지 않는다. API 라우트 파일은 14개 시나리오 어디에도 연결되지 않았다
- 테스트가 아예 없는 기능 3개(시맨틱 검색, 컬렉션, 익스텐션 저장)가 목록으로 보인다

**3. 과거 버그에 대 본 결과 (정직하게).** 2026-07-07 "최근 카드에서 재시도가 안 되던 문제"를 고친 커밋(3238b9c)을 지금 장부에 대 보면:

- 그 수정이 바꾼 파일은 시나리오 6개에 걸린다. 관련 있는 건 "파이프라인 실패와 재시도" 하나인데, 화면을 공유하는 다른 5개까지 재검증 필요가 된다. **연결이 넓어서 잡음이 크다**
- 그리고 장부가 있었어도 **이 버그 자체는 미리 못 잡았다.** 재시도 테스트는 목록 카드만 확인했고, 최근 카드 슬라이더는 확인하지 않았다. 주장("실패하면 재시도 버튼이 뜬다")이 테스트보다 넓었던 것이다
- 배운 점: 장부는 버그를 찾는 도구가 아니라 **"무엇을 다시 봐야 하는지"와 "무엇이 아직 확인되지 않았는지"를 보여 주는 도구**다. 버그를 찾는 건 다음 단계(시나리오를 넓히고 테스트를 쓰는 에이전트)의 몫이다

## 아직 못 한 것 (진행 중)

| 단계                                             | 상태                              |
| ------------------------------------------------ | --------------------------------- |
| 1. 장부, 기계 연결, 해시 기반 신선도, 재검증 CLI | 완료 (`feat/qa-tester`)           |
| E2E 시나리오 실제 실행                           | 아직. 개발 서버가 필요해 건너뜀   |
| 2. 시나리오 작성, 실행, 판정 에이전트 분리       | 다음                              |
| 3. 나이틀리 재검증, 보고서                       | 다음                              |
| 연결 좁히기 (코드 그래프 도구)                   | 나중. 위 3번의 잡음을 줄이는 용도 |

## 발표에서 쓸 문장

> 예전엔 시나리오를 제가 쓰고, 스펙이 바뀌면 다시 썼습니다. 테스트는 매번 전부 돌렸고, 통과하면 무엇이 흔들렸는지는 몰랐어요.
> 지금은 테스트가 확인한 사실을 근거와 함께 장부에 쌓고, 코드가 바뀌면 그 코드에 걸린 사실만 다시 확인하고 있습니다. 파일 하나를 바꿨을 때 8개 중 2개만 다시 보면 됐어요.
> 다만 과거 버그에 대 보니, 장부만으로는 버그를 미리 못 잡았습니다. 장부는 "무엇을 다시 봐야 하는지, 무엇이 아직 확인 안 됐는지"를 보여 주는 도구이고, 그 빈틈을 채우는 게 다음 단계입니다.
